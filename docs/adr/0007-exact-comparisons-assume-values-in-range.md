# Exact comparisons assume values stay in range

An equality gives facts (a pinned value, a bound join key, a dependency, an Equality Group) only when its two sides compare without a lossy coercion (`exact_comparison` in `rules/value_typing.py`). sqlassert decides that from the types on each side, assuming real data: integers stay within their type, decimals within 38 digits. Overflow is not modelled. Whether an engine raises, wraps, widens to DECIMAL or turns to a float on overflow changes no typing, comparison or injectivity fact. An engine where a value really overflows can then hold a row sqlassert did not foresee. That is accepted: guarding every `a + 1` against it would turn the most common key expressions into unproved ones and warnings, to cover a case real data does not reach.

Modelling overflow may be worth studying later, for instance as an opt-in strictness level or a Hazard on arithmetic near a type's bounds. It is left out now because no case seen in real queries needs it.

The rule, the same in every dialect:

- **Exact numbers.** Integers of any width, signed or unsigned (TINYINT to HUGEINT, BigQuery's `INT64`, Snowflake's `NUMBER(38,0)`), decimals with a declared scale, and exact number literals are exact numbers. Any two compare exactly, whatever their widths, precisions or scales. The engine widens both to a common type, which loses nothing in range, and compares by value. Each side has a fixed scale, so one number is one value on each side: `DECIMAL(10,2)` 1.50 equals `DECIMAL(12,4)` 1.5000 and each determines the other. A decimal declared without a scale where it keeps each value's own scale (`unscaled_decimal`: Postgres `NUMERIC`) is not an exact number, since `1.0` and `1.00` are equal but differ.
- **Arithmetic.** `+`, `-`, `*` and unary `-` over exact numbers give an exact number, in every dialect: the widest integer over integers, otherwise a decimal of no claimed precision. `+` and `-` with one side constant are injective in every dialect. A float operand makes the result a float. `/`, integer division and `%` stay untyped (MySQL's `/` of integers is a DECIMAL, Postgres's is an integer).
- **Floats.** A side that is a float (REAL, FLOAT, DOUBLE, a float literal, arithmetic with a float operand) never compares exactly, and the Lossy comparison Hazard warns on it whatever the other side is, typed or not. Floats round, and `-0.0 = 0.0`.
- **Text against a number.** An equality that converts text to a number implicitly is a Lossy comparison Hazard, in every dialect, a string literal included (`int_col = '5'`). Engines that raise on it are not modelled separately: the SQL is wrong either way.
- **String literals beside a date or time.** A string literal compared with a DATE, TIME or TIMESTAMP is taken as that type: SQL has no other portable way to write one. It compares exactly and warns nothing.
- **Number literals.** Each dialect names the type of a literal with a point (`0.1`) and of one with an exponent (`1e0`) (`DialectSemantics.literal_types`). For example, BigQuery's `0.1` is FLOAT64 and Postgres's `1e0` is NUMERIC. The name's kind (exact or float) decides the comparison. Each type is certified with the engine's own type function, as `result_types` are (`typeof` in DuckDB and SQLite, `pg_typeof` in Postgres). Where an engine has none, an exact type needs a cited doc. A float type may be from memory: a wrong one loses proofs and adds a warning, never a wrong proof.

`checked_arithmetic` keeps one meaning: whether arithmetic and CAST of non-null values are non-null (SQLite turns NaN into NULL, MySQL a bad date CAST). Typing and injectivity no longer read it. The other comparison facts, `text_is_binary`, `unscaled_decimal`, `zoned_timestamp_is_instant` and `literal_types`, stay separate `DialectSemantics` fields. With overflow gone they are four independent facts, and grouping them adds a layer that decides nothing.

Out of scope: the caveat a suggested rewrite gives when moving arithmetic onto a narrower type (`sum(b) + 1` to `b + 1`). That is advice about a query that may fail, not a fact an equality proves, so it keeps its overflow wording.

Superseded: the per-dialect gating of arithmetic typing on `checked_arithmetic`; the `Builtin` rule that only checked arithmetic is injective; integers of different widths, and an exact literal against a decimal, as the only exact comparisons across types.
