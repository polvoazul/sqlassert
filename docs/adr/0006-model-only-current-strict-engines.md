# Model only current, strict engines

sqlassert models each engine as its latest release behaves under its default settings, with strict modes on. It does not model older versions, or settings that loosen what the engine checks or accepts: MySQL's non-strict `sql_mode`, `PIPES_AS_CONCAT` or `ONLY_FULL_GROUP_BY` off, Spark with ANSI mode off, Spark 2. When a setting decides a fact, the default decides it; the analysis does not take the weakest reading across all settings. SQL that standard SQL rejects is not given a meaning just because a flavor accepts it, even by default. For example, SQLite accepts a column that is neither grouped nor inside an aggregate. Such SQL is opaque and warns `unsupported-construct`; it is never lowered to something the analysis can prove things about.

The reason is simplicity. Each permissive mode adds a dialect flag, another branch in the rules, and another session for the certifier. It also adds warnings about settings the SQL cannot show, and weaker proofs for the users who run current engines with their defaults. sqlassert is alpha and is meant for current engines, and its users want their SQL stricter, not more permissive. A flavor's lenient quirk is SQL they would rewrite anyway, so supporting it is all cost. Like [ADR 0005](0005-analyze-sql-without-a-connection.md), this never guesses about the SQL. It fixes the engine being modelled: results are sound for that engine. On a legacy version or a permissive setting they may not be.
